# 文档编写与维护规范

本文档定义 `docs/` 的信息架构、事实归属与写作标准，目标是让读者更快找到结果，并避免将易变的源码细节固化成阻碍后续开发的文档。

## 先确定读者与页面类型

动笔前明确读者是谁、要完成什么任务、以及怎样判断完成。参考 Diátaxis 四类文档划分目录职责：

| 类型 | 解决的问题 | 目录位置 |
| --- | --- | --- |
| 教程 | 从明确起点按顺序完成一次任务 | `docs/intro/`（按需建页） |
| 操作指南 | 解决配置、Agent 扩展等具体任务 | `docs/agents/`、`docs/advanced/`（按需建页） |
| 参考 | 查阅命令、开发规范或前端设计基准 | `docs/develop-guides/`、`docs/advanced/` |
| 解释 | 理解系统边界、运行链路与关键决策 | `docs/mechanisms/`、`ARCHITECTURE.md`、`docs/develop-guides/decisions/` |

实质性混合不同类型的内容应拆页，各自通过一句话和相对链接衔接。普通变更与小型调整不要求预先撰写专题页或提案。

## 事实核对顺序与 Owner 边界

核对事实按以下优先级执行：

1. 真实代码入口、公开 API 契约与前端消费逻辑；
2. Service / Repository、ORM Schema、Alembic 迁移与持久化边界；
3. `docker-compose.yml`、环境配置默认值与构建脚本；
4. 与变更风险匹配的自动化测试；
5. `ARCHITECTURE.md`、`docs/mechanisms/` 与 `decisions/` 中的记录。

文档解释系统为何如此组织、边界在哪里以及如何上手使用；不手写易漂移的完整字段清单、逐函数控制流或“不得/禁止”式实现锁死规则，而直接链接到拥有该事实的目录或源码。

## 写作风格

- **肯定句与现在时**：用直接、可核实的现在时陈述执行者、动作、条件与结果；不写“应该/大概/可能”或“以前版本/本次修改”等过程叙事。
- **单一事实来源**：每个完整规则只在一个文档维护，其他地方使用相对路径链接引用。
- **图表克制**：仅在需要表达三项及以上组件关系、状态流转或跨边界时序时使用简短文本图或 Mermaid，且只画当前已存在能力，不把未实现设想混入当前架构图。
- **示例安全**：只使用占位域名、示例值与占位凭据，不写入真实密钥、账号或本地个人绝对路径。

## 变更收口与提交前检查

- 页面新增、移动、拆分或删除时，同步更新所在目录索引与仓库内的全部入站链接，不留下失效锚点。
- 需要记录非平凡架构或生命周期决策时，遵循 [决策记录规范](decisions/README.md)；个人临时推演与任务草稿放在被 `.gitignore` 忽略的 `docs/vibe/`。
- 提交前检查所有相对 Markdown 链接有效，并运行 `git diff --check`；报告验证结果时严格区分已运行通过项与未执行项。
