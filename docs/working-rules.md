# 仓库开发规则

本文档记录 Agent 在仓库中的工作规则和变更边界。`AGENTS.md` 只负责描述项目并指向
本文档，不在入口文件中复制以下内容。

## 1. 工作规则

- 在实现会影响代码、API、数据模型、架构、交互设计、跨模块行为或公开契约的新功能或变更之前，
  先在 `docs/spec/` 下确定所属能力，并创建或更新对应的规格文档。向用户说明拟定的范围和计划，
  明确请求确认，并在获得批准前等待，不得修改生产代码。不需要设计的常规操作（例如安装用户明确
  要求的依赖）不需要新建规格。
- 按能力而不是按源文件组织规格。一个能力可以跨越路由、服务、Worker、仓储、适配器、前端模块和
  测试。不要在 `docs/spec/` 下镜像源码目录，也不要为每个文件创建一个规格。
- 每个 capability 采用以下渐进披露边界：
  - `spec.md` 定义单一的现行预期行为、目标、非目标、不变量、契约、边界情况和验收标准；不保存
    计划历史，也不按讨论轮次追加设计过程。
  - 根目录 `plan.md` 定义一次当前变更的范围、顺序、共享约束、失败处理、验证方式和阅读路由；
    简单变更直接在其中写完实施细节。跨多个可独立实施职责的大型变更，把具体文件修改和代码示例
    放入 `implementation/<responsibility>.md`，根计划不得复制这些正文。
  - 根目录 `tasks.md` 只定义这次当前变更按顺序排列、可独立验证的工作项。
  - `history/<version>/` 保存已完成变更的不可变 `plan.md`，有对应任务快照时同时保存
    `tasks.md`；历史文件不是当前契约，不保留 `implementation/`。
- 每个当前 `plan.md` 必须在标题下方立即声明 `计划版本：vX.Y.Z`。未实施计划在原处修订时不得
  修改版本号，也不得产生历史副本；只有上一版本已经实施并开始新的实施范围时，才递增版本号。
- 一个计划版本完成后，如果存在 `implementation/`，先按根计划路由顺序把切片正文合并回完整
  `plan.md`，并从 `tasks.md` 删除切片路由；再把 `plan.md` 和 `tasks.md` 移入
  `history/<version>/`，删除当前 `implementation/`。不得把多个历史版本折叠、附加或复制到当前
  `plan.md`、`tasks.md` 或 `spec.md` 中。
- 讨论形成新的设计结论后，尚未实施的 `spec.md`、`plan.md` 和 `tasks.md` 必须在原处删除或改写
  已被取代的内容，保持单一、完整的现行契约；不得按讨论轮次机械追加新段落。
- 默认加载顺序是 domain README -> capability `spec.md` -> 当前 `plan.md` / `tasks.md` ->
  当前任务对应的 `implementation/<responsibility>.md`。不得递归扫描 `implementation/` 或
  `docs/spec/`；只有用户要求追溯、回归或比较历史设计时，才读取指定的 `history/<version>/`。
- 当一个 `spec.md` 已包含多个可以独立定位、独立验收的职责时，按能力边界拆成命名明确的
  capability 或 sub-capability，并由上级 README 路由；不要按日期、版本或 `part-1/part-2`
  机械切文件。是否拆分由职责边界决定，不使用固定行数阈值。
- 规格和计划的目标、实施步骤和验收范围必须写成正向、可执行的内容。除明确标注的非目标和范围
  限制外，列出的每个行为、文件修改、示例和验证步骤都必须对应实际会执行的工作。
- 非简单的 `plan.md` 必须为核心契约和控制流提供具体示例。每个示例都必须注明目标文件以及负责
  它的函数、类、方法或文档章节。只有纯文字的计划和没有落点的代码片段都不完整。
- 通过规范文档路径和稳定的需求 ID 引用相关能力。不要在多个规格中重复同一个契约、不变量或示例。
- `plan.md` 和 `tasks.md` 通过需求 ID 指向 `spec.md`，只写本次实现差异和落点，不复制完整需求正文。
- 实施切片按运行时、持久化、Worker、前端等真实责任边界命名，并声明关联需求与 Task ID；不要按
  源文件逐个拆分，也不要使用 `part-1/part-2`。
- domain README 和 capability README 只承担路由职责，保持在一屏左右；不复制 spec、plan、tasks
  的正文，也不逐项展开历史内容。
- 创建或修订规格、计划时，如果 `ponytail` 技能可用，必须先使用它识别并从方案中剔除不属于最小
  可用端到端实现的新增文件、抽象、组件和兼容性路径。若结论涉及移动或删除现有文件，仍须按下一条
  规则先获得用户批准。
- 保留不属于本次已批准变更范围的现有目录结构、模块边界和公开契约。如果任务确实需要移动或删除
  现有文件、改变既定所有权、重构现有模块或修改公开契约，必须先说明必要性及影响，并等待用户明确
  批准。
- 对于已经批准被替换的应用路径或公开契约，不保留向后兼容；删除旧路径，不要增加兼容层、遗留回退、
  旧新两套实现或过渡性兼容迁移。
  正常的 Alembic 数据库 schema 迁移仍然必须保留。
- 选择能够完整满足当前需求的最简单实现。避免推测性的抽象、配置、扩展点和间接层。
- 分层发展系统。从能够端到端工作的最小版本开始，在已有可工作的产品之上逐层增加能力。每个实施
  步骤都必须让仓库保持完整且可测试。不要为了尚未完成的复杂度牺牲可工作的产品。
- 保持组件模块化，并清晰分离各自关注点。
- 当成熟、维护良好的库能够降低整体复杂度或提升可靠性时，优先使用它们。先利用已有依赖，再自行
  编写实现。假定某项能力不存在之前，先检查库文档和类型定义。
- 面向长期做架构决策。不要接受一个明确打算以后替换的临时方案。
- 提交前反问自己：资深工程师是否会认为结果过度设计、过度防御、嵌套过深或拆分过度？如果是，先
  简化它。
