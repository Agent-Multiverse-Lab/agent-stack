# 功能开发规则

1. **只有重大改动或新增 feature 才做任务拆分和设计文档。** 普通修复、小范围调整和明确的单点需求直接实现，不创建或更新 `spec.md`、`plan.md`、也不为开始编码额外请求确认。

2. **文档设计原则**

   - 从第一性原理分析任务，极简的描述当前任务的核心。
   - 文档设计以完成局部闭环，再处理整体；目标完成后删除冗余内容并收敛方案。
   - 文档只写任务中要做的事，不写排除项。
   - 不得从字段名、缓存位置、历史实现或技术选型反推需求；没有依据或需求时，不得新增概念、字段、状态、中间层或兼容路径。
   - `plan.md` 只包含“当前任务、任务目标、如何修改、实施步骤（计划），验收标准”
   - `spec.md` 记录实现细节，包括类定义、接口、数据契约和改动前后的 Mermaid 流程图。
   - 跨多个职责时增加 `implementation/` 切片。
   - 计划完成后，将 `plan.md` 移入对应的 `history/<version>/`。

3. **按能力拆分，不按文件拆分。** 任务和实施切片应围绕可独立交付、独立验收的能力，并按前端、持久化、运行时等真实职责划分；不按源码文件、日期、篇幅或 `part-1/part-2` 机械拆分。

4. **选择最简单的完整方案。** 优先复用现有契约、组件和依赖，不增加推测性抽象、重复状态、临时方案或兼容层。从最小可用的端到端版本开始，每一步都应保持系统可工作，再逐层增加能力。

5. **尊重现有边界。** 保留任务范围外的目录、模块和公开契约。需要移动或删除文件、改变模块所有权、重构既有边界或修改公开契约时，先说明必要性和影响，并取得用户明确批准。

6. **文档和验证必须真实。** 讨论产生新结论后，直接更新尚未实施的现行文档，不叠加过期方案。只记录实际准备实施的内容，只报告实际执行过的检查、测试和运行结果。
