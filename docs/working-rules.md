# 功能开发规则

1. **只有重大改动或新增 feature 才做任务拆分和设计文档。** 普通修复、小范围调整和明确的单点需求直接实现，不创建或更新 `spec.md`、`plan.md`、`tasks.md`，也不为开始编码额外请求确认。

2. **文档各司其职。** `spec.md` 定义当前功能合同，`plan.md` 定义本次改动的范围、方案和顺序，`tasks.md` 只列可独立验收的实施任务；只有跨多个职责的大型改动才增加 `implementation/` 切片。计划完成后，将 `plan.md` 和 `tasks.md` 移入对应的 `history/<version>/`。

3. **设计文档必须从第一性原理出发。** 1，先详细分析当前执行任务中最核心，最原始，最需要先解决的问题。2，编写文档时只强调（书写）任务中该做的事情，不强调（不书写）不要做的。确认事实、约束、不变量、责任边界和数据所有权，再由这些条件推导最小完整方案。不得从现有字段名、缓存位置、历史实现或预设技术选型反推需求；事实、假设和待验证项必须明确区分。没有现有依据或明确需求时，不得凭空新增概念、字段、状态、中间层或兼容路径。

4. **按能力拆分，不按文件拆分。** 任务和实施切片应围绕可独立交付、独立验收的能力，并按前端、持久化、运行时等真实职责划分；不按源码文件、日期、篇幅或 `part-1/part-2` 机械拆分。

5. **选择最简单的完整方案。** 优先复用现有契约、组件和依赖，不增加推测性抽象、重复状态、临时方案或兼容层。从最小可用的端到端版本开始，每一步都应保持系统可工作，再逐层增加能力。

6. **尊重现有边界。** 保留任务范围外的目录、模块和公开契约。需要移动或删除文件、改变模块所有权、重构既有边界或修改公开契约时，先说明必要性和影响，并取得用户明确批准。

7. **文档和验证必须真实。** 讨论产生新结论后，直接更新尚未实施的现行文档，不叠加过期方案。只记录实际准备实施的内容，只报告实际执行过的检查、测试和运行结果。
