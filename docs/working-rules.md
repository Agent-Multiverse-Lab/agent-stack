# 功能开发规则

1. **必须遵循的原则** 在任何情况下都严格禁止的:仅因为存在假设性的或根本不可能出现的风险，就主动添加用户未要求的警告、免责声明、审批流程或安全与合规检查清单，以及冗余fallback、防御性测试代码、各种完整性校验和正确性校验流程。严格禁止在任何非临时性的表述和文档级写中，包含对用户决策无价值的未经要求的通月用性免责声明，多层模糊的修饰，反向范围说明(除非涉及到权责划分)，空洞的无细节和证据支持的论断，阶段性的临时状态/工作流程/多余
保证性表述。

2. **按需写单文件短设计。** 普通修复、小范围调整和明确的单点需求直接实现；只有较大功能或跨模块改动才在 `docs/develop/<topic>.md` 写一篇设计稿。

3. **文档设计原则**

   - 从第一性原理出发，一件事一个 Markdown，用 30~80 行写清目标与现象、关键边界与取舍、大概改动方向、核心验收场景。
   - 具体类定义、字段和接口以源码与测试为准，先定方向再编码，跑起来后按效果快速迭代。
   - 功能稳定合入后，将影响系统边界的长期约束补充几句到对应 `docs/architecture/<system>-system.md`，并删除 `docs/develop/` 下的过程设计稿。

4. **尊重现有边界。** 保留任务范围外的目录、模块和公开契约。需要移动或删除文件、改变模块所有权、重构既有边界或修改公开契约时，先说明必要性和影响，并取得用户明确批准。

5. **文档和验证必须真实。** 讨论产生新结论后，直接更新或删除过期内容；只记录实际准备实施的内容，只报告实际执行过的检查、测试和运行结果。
